# Priority 0 — Fix CUDA driver compatibility semantics

The current compatibility model is too strict.

Review these files first:

```text
src/cuda_doctor/checks/driver_checks.py
src/cuda_doctor/checks/pytorch_checks.py
src/cuda_doctor/compatibility/cuda_driver.py
src/cuda_doctor/compatibility/_util.py
src/cuda_doctor/data/cuda_driver_compatibility.json
tests/unit/test_compatibility.py
tests/unit/test_checks.py
README.md
```

## Problem

The current code treats the CUDA version reported by `nvidia-smi` as a strict runtime ceiling.

For example, code currently effectively reasons:

```text
nvidia-smi reports CUDA 12.2
local toolkit is CUDA 12.6

12.6 > 12.2
=> ERROR
=> binaries built with CUDA 12.6 will fail
```

That conclusion is too strong.

Starting with CUDA 11, NVIDIA supports CUDA Minor Version Compatibility.

Within supported conditions, an application built with a newer CUDA minor release can run on a driver whose reported CUDA UMD version is an older minor version within the same major family.

There are important caveats:

- features requiring a newer driver may fail;
- PTX generated by a newer toolkit may require a newer driver;
- forward compatibility packages may change compatibility behavior;
- architecture-specific constraints may also matter.

Therefore:

```text
toolkit minor > nvidia-smi CUDA minor
```

MUST NOT automatically become a hard ERROR.

Likewise:

```text
torch.version.cuda minor > nvidia-smi CUDA minor
```

MUST NOT automatically become a hard ERROR.

# Use NVIDIA's minor compatibility model

For CUDA 11+ treat driver compatibility primarily by CUDA major family.

At minimum encode the documented minor-version-compatibility baseline such as:

```text
CUDA 11.x:
Linux >= 450.80.02
Windows >= 452.39

CUDA 12.x:
Linux >= 525.60.13
Windows >= 528.33

CUDA 13.x:
use the current NVIDIA-documented minimum for CUDA 13 minor compatibility
```

Before hardcoding values, verify them against current official NVIDIA CUDA Compatibility / Toolkit Release Notes.

Do NOT confuse:

```text
driver bundled/released with CUDA Toolkit X.Y
```

with:

```text
minimum driver required through CUDA minor-version compatibility
```

These are different concepts.

The current JSON data appears to mix these concepts.

Correct the data model and comments.

If useful, make the data explicitly describe major-family minor compatibility:

```json
{
  "11": {...},
  "12": {...},
  "13": {...}
}
```

or another clear representation.

Prefer correctness and clarity over preserving the existing JSON schema.

# DRV002 required behavior

Rework `DriverRuntimeCompatibility`.

It must NOT say:

```text
Binaries built with this toolkit will fail
```

simply because:

```text
toolkit CUDA minor > nvidia-smi CUDA minor
```

within the same CUDA major family.

Desired conceptual behavior:

### Case A

```text
driver satisfies CUDA major-family minor compatibility minimum
toolkit major == supported driver CUDA major
toolkit minor > reported driver CUDA minor
```

Do NOT emit ERROR.

Optionally emit INFO explaining:

```text
The local toolkit is newer than the CUDA UMD version reported by the
driver, but CUDA minor-version compatibility may allow applications to
run within this CUDA major family.

Some newer driver-dependent features and PTX may still require a newer
driver.
```

Avoid excessive noise if this information is not useful.

### Case B

Driver is below the NVIDIA-documented minimum for the toolkit/runtime's
CUDA major family.

This may be ERROR or WARNING depending on certainty.

Provide evidence and actionable recommendations.

### Case C

CUDA major family itself is unsupported by the installed driver.

This can be considered a strong incompatibility signal.

Still word conclusions carefully because CUDA forward-compatibility
packages may exist on supported systems.

### Case D

Compatibility data is unavailable.

Return UNKNOWN / no hard verdict.

Do NOT infer compatibility.

# Priority 0 — Unknown/future CUDA versions must remain UNKNOWN

Review:

```text
src/cuda_doctor/compatibility/_util.py
src/cuda_doctor/compatibility/cuda_driver.py
src/cuda_doctor/compatibility/compiler_cuda.py
tests/unit/test_compatibility.py
```

Current behavior uses:

```python
nearest_lower(...)
```

for unknown CUDA versions.

There is currently a test effectively expecting:

```text
CUDA 14.0
→ use CUDA 13.0 compatibility requirements
```

Remove that behavior.

This is unsafe for a diagnostic tool.

A future CUDA major version MUST NOT inherit compatibility rules from
the previous major.

For example:

```text
CUDA 14.0 + only CUDA 13.x knowledge available
=> compatibility = UNKNOWN
```

not:

```text
=> CUDA 13 requirements probably apply
```

For unknown minor versions within a known CUDA major family:

- use a major-family compatibility rule only when NVIDIA documents that
  the rule applies across the entire major family;
- otherwise return UNKNOWN.

Do not silently infer exact minor-version compiler support from an older
minor version.

Compiler compatibility should also avoid claiming compatibility for
future CUDA releases using stale nearest-lower rules.

Unknown is better than a false green result.

Add regression tests.
